# canon-pack-builder（Canon Engine 历史包生成工具）

把一部作品的剧情原文（游戏脚本、维基页面……）做成 Canon Engine 的历史包（`.canon.json`）。

机械的部分全由代码完成：下载、解析、谁在场、日期、时间线、组装、校验。只有"读懂剧情写摘要"这类需要理解的部分才交给便宜的模型（默认 DeepSeek Flash）。

目前有两个来源适配器：**Atlas Academy（FGO 游戏数据，`atlas`）**和**维基篇章（`wiki_arcs`，魔禁用）**。核心流程与具体作品无关，换一部作品只需要换一个适配器。

## 准备

1. 需要 Python 3.10 以上（只用标准库，不用 `pip install`）和 Node（用来运行 Canon Engine 自带的 `canon-lint`）。
2. 把 `config.example.json` 复制为 `config.json`，在 `llm.api_key` 填入你的 DeepSeek API key。也可以不写进文件，改用环境变量 `CPB_API_KEY`。
3. `config.json` 里的 `canon_lint` 指向 Canon Engine 的 `dist/canon-lint.mjs`。工具放在 Canon Engine 仓库的 `tools/pack-builder/` 下，默认路径 `../../dist/canon-lint.mjs` 就是它。
4. 维基来源（`wiki_arcs`）下载时用 Playwright：`npm i playwright && npx playwright install chromium`，或用环境变量 `PLAYWRIGHT_PATH` 指向已装好的 Playwright。

`config.json` 和 `work/` 都不会进 git：前者放着你的 key，后者放着下载的原文和生成的包。

## 用法

在本目录下运行：

```
python -m cpb <命令> -p <项目>
```

`-p` 是 `projects/` 下的项目名，默认 `fgo-cn`。另有 `fgo-cn-sample`（只含冬木和奥尔良两章），适合先试一下效果。

| 命令 | 做什么 | 花钱吗 |
|---|---|---|
| `fetch` | 下载数据和剧情脚本，解析成"语料"，扫描日期，生成骨架报告 | 免费 |
| `estimate` | 估算剩下的模型步骤要花多少钱 | 免费 |
| `summarize` | 模型逐个关卡写结构化摘要（起因/动机/经过/结果……） | 💰 主要花费 |
| `chapters` | 模型逐章判定 HARD/SOFT/FREE、事件关联、伤势何时结束等 | 💰 少量 |
| `entities` | 模型为人物、地点、组织写一句话描述和别名 | 💰 少量 |
| `build` | 代码排时间线、组装包、跑 `canon-lint` 和质量检查、写报告（之前生成过的开局状态、死亡判断、状态判断、常态、思考方式、关系会一并写进去） | 免费 |
| `mind` | 模型为包里有维基页面的人物写「思考方式」：遇事愿意花多少心思想（很少 / 看情况 / 总在想）、想得多好、怎么解决问题；写进包里（`--pack`、`--out` 同上） | 💰 少量 |
| `relations` | 模型为人物对写「关系」：彼此是什么关系、怎么看待和对待对方、在一起时什么样，按改变关系的事件分阶段；有核对过的关系时只作建议，写出对照 | 💰 少（魔禁约 500 对：列事实约 $0.5，写约 $0.3） |
| `address` | 模型为核对过的关系提出各段各方的「称呼」（只写不是直接叫名字的，带频率和场合），写出 `work/<项目>/out/address-review.txt` 供人逐条读；`--apply` 放进核对过的关系 | 💰 极少（魔禁 486 对约 $0.25） |
| `golden` | 核对过的关系：第一次从读过的包生成 `projects/<项目>.relations.json`；之后 `--adopt 甲\|乙 --note "…"` 把读过的生成结果收进来 | 免费 |
| `impacts` | 模型读每个事件的结果、后续、影响，列出事件对事件以外的世界留下、而效果里还没有的改变（谁被关押、谁离开、地点被毁、东西易手），每项带持续多久；提议存在 `work/<项目>/impacts.json`，等人核对 | 💰 极少（魔禁约 $0.05） |
| `ends` | 模型为每条状态（所在、伤势、状态、地点状况、形态）提议结束方式：持续、几分钟后自行结束、到某个事件结束，或根本不该是状态（删去）；提议存在 `work/<项目>/ends.json`，等人核对 | 💰 极少（魔禁约 $0.09） |
| `start` | 开局状态：模型按每个组织自己的页面和包里的成员变化，说出它在故事里出场时的成员和首领；然后重新 `build` | 💰 极少 |
| `deaths` | 死后仍在场的人：模型判断是真死（之后是尸体、回忆、幽灵）、复活，还是根本没死；然后重新 `build` | 💰 极少 |
| `nature` | 模型为包里的人物写「常态」：能力、体质或非人之身在日常里的样子，按事件分版本；写进包里（`--pack` 指定别的包，`--out` 另存） | 💰 少量（魔禁 553 人约 $0.25） |
| `run` | 从 `fetch` 到 `build`（进入花钱的步骤前会先问你）；之后依次 `deaths`、`start`、`impacts`、`ends`、`nature`、`mind`（各自的结果在下次 `build` 时自动套用），然后核对（见「人工核对」） | 💰 |
| `status` | 查看每章做到哪一步了 | 免费 |

常用选项：
- `--chapters w100,w101`：只处理这几章。
- `--limit 5`：只摘要 5 个关卡，用来试水。
- `--mock`：用假模型跑通整个流程，不花钱，结果放在单独的文件夹。
- `--yes`：`run` 时不再询问。
- `--offpeak`：只在非高峰时段调用模型，到了高峰就停（已完成的保留，之后再跑同样的命令继续）。

推荐流程：

```
python -m cpb fetch -p fgo-cn-sample       # 先看骨架：work/fgo-cn-sample/skeleton.md
python -m cpb estimate -p fgo-cn-sample
python -m cpb run -p fgo-cn-sample         # 约 $0.2；结果在 work/fgo-cn-sample/out/
```

对试做版满意后，再对 `fgo-cn` 做同样的事。

### 常态（`nature`）

在建好的包上运行（它要用包里的事件）。每个人一次调用，输入是包里的描述、这个人参与的事件（分成开局前的背景和开局后的事件，附包里记录的此人状态变化）和维基上此人的页面。代码再做这些检查：

- 版本 1 是开局（第 0 天）时的样子；之后的版本挂在事件上，要说明持续多久（`for_good` / `until` / `passing`）。临时状态（`passing`，或不到 14 天就结束）丢弃；受伤本身从不算版本，包里本来就记着伤势。
- 后面版本里「新出现的东西」（十字架、电极），开局那一版不能已经提到。
- 版本所在的事件没有记录这个人自己的变化时，要从事件摘要或维基原文引出依据，否则丢弃。
- 不写剧情：和此人同场过的人物，名字不许出现在「平时 / 使用 / 旁人」里（会退回重写）；再由一次检查删掉只发生过一次的事、绰号、传闻、台词。

- 最后一步按版本判断「能力能得知什么」（`perceives`：读心、记忆、情绪、看穿遮挡、定位、识破谎言、读取过去，附条件），Canon 据此决定读心者面前秘密是否开放。只看已写好的常态，一个人一次很短的调用（魔禁 305 人约 $0.015）。

结果在 `work/<项目>/nature/<人物 id>.json`（含丢弃的版本和删掉的句子），可以逐个查看。

### 思考方式（`mind`）

给包里有自己维基页面的人物写（路人、只在剧情里出现过的人没有）。每人一次调用，输入是包里的描述和维基页面。写倾向（`deliberation`）、水平（`sharpness`）和做法等几项，倾向和水平分开：肌肉派可以很敏锐，只是平时不想。和常态一样只写规律、不写剧情：和此人同场过的人物名字不许出现（会退回重写）。资料太少写不出来的回答 `none`。Canon 在游戏里照这个写人，并替「看情况」「总在想」的人做角色盘算。结果在 `work/<项目>/mind/<人物 id>.json`；`build` 时会一并写进包里。

### 关系（`relations`）

哪些人物对由代码决定，不问模型：一是某人的维基页面在人际关系里列出的人（`;` 条目，或页面里的人名小标题；能力、作中行动等节不算），两边都要能唯一对上包里的人；二是在包里共同出现 8 件以上事件的人。

每对调用两次模型。

第一次列事实。输入是两人的描述、两边页面写对方的条目、各自页面里提到对方的句子，以及两人共同的事件（按时间排）。输出：
- 故事开始前是否已认识（`known_before_start`，认识的写怎么认识的）；
- 两人之间每一条长期成立的事实，各标上从哪件共同事件起成立（开局前就成立的标 `before`）；
- 各阶段从哪件事件开始：第一阶段从故事开始（认识的）或两人初次打交道的事件开始，之后只在关系本身长期改变处另起一段。
- 资料里没有真正往来的回答 `none`。

每段能看到哪些事实由代码按日期决定：只给起点当时或之前成立的事实。模型自己挑的话，8 月的一段会写进 12 月的事。

第二次照各段的事实写。每段写 `bond`（是什么关系，写出它的几面，不是一个标签）、每一方的 `sees`（怎么看待、对待对方），以及 `together`（在一起时的样子）。称呼另由 `address` 写（见下）。后面的阶段是整段关系此刻的样子：新事实加在仍然成立的旧事实上，不是替换（变得信任对方的两个对手，仍会斗嘴）。只写常态，不复述剧情。

各方的 `who` 必须用两人的名字，不用 A/B：用 A/B 时模型会把一方的看法写到另一方名下。

两次回答都由代码检查，不合格的退回重写：
- 事实：时间是 `before` 或列出的共同事件；`before` 只在开局前认识时用，事实里写的日期不能在开局之后（只有开局前共同事件的一对，曾把整段故事写成 `before`）；每段（包括从事件开始的第一段）在起点都有事实成立；
- 文字：段数与给的一样；`bond` 是状态，不是「从…转为…」；后面的阶段两方都写；两方都写时 `together` 不空；不夹英文；不写「资料没给出这一方的态度」这类话，没有资料的一方不写。

检查改严之后，已缓存的回答也会再查一遍（`recheck`），只重问不合格的那些，不用为此改版本号让全部重来。

结果在 `work/<项目>/relations/<甲>__<乙>.json`。

**生成的关系不直接进包。** 生成器不可信：以前包里很多错，都是直接用了生成的结果。流程是：
1. 生成（`relations`），把所有关系一对一对读完，错的手改；
2. 读过、改过的存成核对过的关系 `projects/<项目>.relations.json`（第一次用 `golden` 从读过的包生成），这是唯一的来源：`build` 放进包里的就是它，别的更正和统一写法都不会再改它；
3. 读的时候发现的每一类错，都改进生成器（提示或代码检查），再跑一次 `relations`，看新的结果和手改的接不接近；
4. 无论接不接近，包里用的都是核对过的那份。

有核对过的关系时，`relations` 跑完会写对照 `work/<项目>/out/relations-compare.json`：生成器新提出、要读的人物对（核对文件 `rejected` 里读过、判定不是关系的不算），生成器不再有的，阶段起点不同的，文字不同的，以及手改过的那些对（有 `notes` 的）生成器现在是否给出同样的阶段起点。读过的新人物对用 `golden --adopt 甲|乙,丙|丁 --note "读过……"` 收进来；要改就直接改核对过的关系文件，每对的 `notes` 写改了什么、为什么。

放进包时，合并过的人换成保留的 id；某段的起点事件已不在包里的，这一对不放进包，列入「核对文件里的更正没有对上」，在核对过的关系里改。

### 称呼（`address`）

GM 最常弄错的是谁怎么称呼谁，所以称呼单独成一栏（每一方的 `address`），只写有特殊之处的：光看全名猜不出来的叫法——外号、头衔、敬称（御坂同学）、蔑称、昵称、亲属称谓，或只叫姓、只叫名。直接叫全名的不写，单独的人称代词不写；什么都不写时 GM 照故事里的习惯叫名字。很多人对很多人没有可写的称呼。每个称呼带频率：`always`（只这样叫，单独一个，如黑子叫美琴「姐姐大人」）、`usually`（平常这样叫）、`sometimes`（有时，要写 `when`：什么场合，如调侃时、跟别人提起时）。

这一步给每对核对过的关系调用一次模型：输入是核对过的各段（是什么关系、两方怎么看对方）、各段起点时成立的事实（`relations` 缓存里的，由代码按日期分给各段），以及两边页面写对方的条目和讲到怎么称呼对方的句子。各段只写那时在用的称呼，后来才有的放到开始用的那段。代码检查：称呼本身不带括号、引号、「或」和说明，一条一个；不能有日文假名；不能是对方的全名；`sometimes` 要写场合；`always` 只能单独一个。

结果是提议，不直接进包：`work/<项目>/out/address-review.txt` 逐对列出提议（和以前的写法对照），人全部读完再 `address --apply` 放进核对过的关系，然后像别的内容一样在核对文件里手改。魔禁这一轮的经验：模型常把一句话里的骂法、单独的「你」、对方的全名当成称呼，把常用的叫法标成 `always`，也会编出原作里没有的外号；只叫姓（日本人名）或只叫名（西方人名）是默认叫法，除非同一方还有别的称呼需要它作对照，不写。

游戏里，Canon 把场景里在场的人两两之间（以及和文中提到的人之间）此刻的关系写给 GM。玩家角色和原作人物一样：Persona 给出开局的关系，之后按游戏里发生的事更新。

### 质量检查（每次 `build`）

报告 `work/<项目>/out/report.md` 开头有一节「质量检查」（`cpb/checks.py`，代码检查，不调用模型），把做包时遇到过的每一类问题都在整个包上查一遍，命令行也会打出一行 `checks: N problems …`。「问题」应为 0：人物的一时状态挂了三周以上、成员在组织出场之前加入、组织瓦解后仍有成员、几个实体共用一个名字、几个人写成了一个实体、以别人名字开头命名又没有自己页面的人物、主要人物缺失、同一天同标题的事件、HARD 事件缺少要求或结果、没有事件的篇章、时间和文中不符（窗口的开始时刻、日期、时段与事件自己的文中时间对不上；核对文件里写明理由的除外）、canon-lint 警告未处理（每条警告要么改掉，要么在核对文件 `warnings` 里写明为什么接受）、历史包和已发布的那份（项目的 `pack.release`）不同版本号却没提高（`pack.pack_version` 要手动提高：旧引擎读不了的格式或意思变了提大版本，内容变了提小版本）。「复核」是各步骤的判断结果，供人过目：日期离篇章远的事件、死后仍在场的人、挂得久的组织状态、不在任何事件里的人物、没有相关实体的事件。项目的 `checks.leading` 列出必须在、有页面就必须有思考方式的主要人物；`checks.dates` 列出要看组织一览的日期。

### 开局状态（`start`）

事件只写谁加入、谁离开；一个组织在第一次变化之前有谁，得看它自己的页面。这一步给每个有页面或有成员变化的组织调用一次：输入它的页面、包里它的成员变化（按时间）、它最早的几次出场，以及页面或变化里点过名的人物（只能从这些人里选，代码检查 id）。结果在 `work/<项目>/start/<组织 id>.json`；`build` 时每个起始成员从他自己和这个组织都已在故事里起才算加入（组织从第一次被提到的事件算起；在那之后第一个和他或这个组织有关的事件上加入；他先被写到离开，就在离开之前），不放在“故事开始时”，否则后来才成立的组织（格雷姆林）在故事开始时就有成员。哪个事件里都没有的人才进初始状态。组织的状态写明瓦解、覆灭、解散时，成员和首领一并清空。

### 死后仍在场（`deaths`）

一个片段写了“死亡”，这个人之后却还在别的片段的在场人物里：可能真死了（之后是尸体、回忆、幽灵、替身），可能复活了，也可能只是被认为死了（落海获救）。这一步把每个这样的人的死亡片段和之后出场的几个片段交给模型判断。复活的在之后第一次出场时活过来，并回到死亡时离开的组织；没死的，死亡改为“下落不明（被认为已死亡）”，到再出场时结束。判断存在 `work/<项目>/deaths.json`，`build` 自动套用。

### 人工核对（`projects/<项目>.review.json`）

包里每个事件的时间、每条状态持续多久、事件对之外世界的影响，都必须明确，不能靠猜：

- **时间有多确定**：`build` 按资料给每个事件定窗口和精度——资料给了钟点的是 `range`（确切时间），只说了上午/傍晚的是 `part_of_day`，只有日期的是 `day`，只说「10月初某日」的是 `days`，只有月份、年份的是 `month`、`year`。不确切的窗口在游戏里就是「这段时间里的某个时候」，不会编一个钟点。同一个故事里几件事共用同一个不确切窗口（同一个傍晚的 8 件事），在时间线和游戏里就成了同时发生；它们其实一件接一件，所以 `build` 把这样的每一件都标出来（「与同一窗口的 n 件事共用时间（第 k/n 件）」），由人在 `times` 里给每件一个按先后、在原窗口内的时间，说明以「编辑推定」开头（原作没给钟点，游戏需要一个；时间线上显示为「约 …（编辑推定）」，理由只留在核对文件里）。资料没给日期、只知道先后的，时区不是主时钟的，文中说的时段和先后顺序对不上的，`build` 会在事件上标出来，等人决定。
- **状态持续多久**：每条效果都带 `until`——`lasting`（直到之后的变化）、`{"minutes": n}`、`{"event": id}`（到那个事件结束）。谁加入谁离开、生死、持有、知道的事本身就是持续的；其余的（所在、伤势、状态、状况、形态）按 `ends` 的提议，等人核对。
- **事件以外的影响**：按 `impacts` 的提议，等人核对。

人的决定记在 `projects/<项目>.review.json`（进 git）：`times`（事件 id → 起止、精度、说明）、`ends`（「事件|实体|谓词」→ 值和 `until`，`"drop"` 表示这条状态是摘要读错了，连同结果一起去掉）、`impacts`（事件 id → 核对过的影响列表）。每次 `build` 都套用它，所以重建不会丢掉人的决定；还没有决定的，事件上写 `review`（为什么要核对），`canon-lint` 拒绝这样的包——没核对完的包交不出去。决定是按值记的：模型重写了摘要、状态的值变了，这一条就重新等人决定。

HARD 事件要求的结果全被核对删去时，事件改为锁定它还写着的效果；什么都不写的事件不再是 HARD。

摘要和模型读错的东西，人的更正也记在核对文件里（`cpb/corrections.py`，每次 `build` 套用）：

- `duplicates`：同一件事讲了两遍（「a|b」→ `same`、`keep`），并入保留的那件。
- `events`：事件 id → `drop`（错的效果，成员可只去掉名单里的某几人）、`unlink`／`link`（被名字连错、漏连的实体）、`recast`（把一个实体换成另一个：冒牌上条、独角仙05）、`knowers_drop`、`texts`（这件事里的改字；改成空的一段会去掉）。
- `entities`：实体 id → `merge_into`（同一个东西两个实体：引用全部移过去，名字成为别名）、`drop`、改 `name`／`kind`／`description`／别名。
- `texts`：全包统一的写法（事件、篇章、实体描述、效果里的文字；`people: true` 的改在常态、思考方式里；核对过的关系不受它影响）。
- `start`：组织 id → `drop`（开局名单里不该有的人：前成员、只是打过交道的人）、`at`（某人在哪个事件加入，`"start"` 为初始状态）。开局名单在人的更正之后才放（合并、改认、生死都已是人定的），不会把当时已死的人放进组织；组织从第一次被事件提到算起（不只是被连上的事件）。
- `events.<id>.after_drop`：摘要写错的先后关系（「那件事引出这件事」），在关系变成边之前去掉，不再用来收窄时间窗口。
- `minds`：常态（按 `from_event`，开局为 `start`）与思考方式的字段改写。
- 关系不在核对文件里改，改核对过的关系 `projects/<项目>.relations.json`（见「关系」）。

每条更正都必须还对得上：对不上的（文字改了、事件或实体没了）列在检查「核对文件里的更正没有对上」。

### 包的约定，和检查它的代码

包交出去的标准只有一条：**canon-lint 0 错误、0 警告，`checks: 0 problems`**。每条约定都有代码检查，不靠人记得（2026-11 修包十余轮的教训：没有检查的原则只是愿望，整批“按资料”收下的不是核对）。

| 约定 | 检查 |
|---|---|
| 每条效果写明到何时结束（`until`）；结束事件存在、不是自己、不早于本事件 | canon-lint（错误）；代码加的效果（死亡不成立时的「下落不明」「重新出现」）自带结束 |
| 没有人没决定过的东西（`review` 标记） | canon-lint（错误） |
| 确切时间（minute/range）必须有出处：文中有时刻，或核对文件写明来由 | 检查「没有出处的确切时间」 |
| 窗口和文中一致：开始时刻、日期、时段 | 检查「时间和文中不符」；人写明理由的不同列在复核「人定时间与文中不同」（说明会让检查放过它，所以理由要被看到） |
| 一个故事里的事不共用一个不确切的窗口 | `review` 标记（canon-lint 错误） |
| 窗口守先后：后一件不比前一件开始得早，前一件不比后一件结束得晚（builder 用先后关系收窄不确切的窗口） | 检查「窗口与先后关系不符」；canon-lint 对确切时间的重叠 |
| lint 警告要么改掉，要么在核对文件 `warnings` 写明理由 | 检查「canon-lint 警告未处理」 |
| 内容变了版本号就提高 | 检查「历史包变了，版本号没变」 |
| 人物一时的状态不挂三周以上；组织瓦解后无成员；成员不早于组织出场；HARD 有要求和结果；同日同名事件不重复 | 各自的检查 |
| 谓词放在对的实体上：成员、首领在组织上；持有者在物上（不是自己）；生死、伤在人身上；完好与否不写在人身上 | 检查「谓词与实体种类不符」 |
| `alive=True` 只给此前死过的人（出生不算）；死人不加入组织；死去的首领卸任，复活后回来 | 检查「没死过的人「复活」」「死人加入组织」；`changes.complete` |
| 治疗、包扎、「已稳定」不是新的伤 | 检查「把治疗写成了伤」 |
| 正文里没有做包时的笔记（待核对、见维基、考据）、没有没译的英文、没有做包用的说法（事件编号、beat、arc 由代码换成标题与中文） | 检查「正文里有研究过程的话」「中文正文里夹着英文词」；`assemble.plain_text` |
| 常态、思考方式、关系没有空项、半句；名字没有截断的引号；实体描述说得出是谁 | 检查「常态、思考方式、关系的文字残缺」「名字、别名里的引号不成对」「空洞的实体描述」 |
| 关系的每一段从两人都在的事件开始；共同事件很多的人物对有关系（没有的列出来看） | 检查「关系的阶段不在两人共同的事件上」；复核「共同事件很多却没有关系的人物对」 |
| 人的更正都还对得上 | 检查「核对文件里的更正没有对上」 |

发现新的一类问题时，先加一条检查（在旧包上验证它能查出来），再修数据；只修数据、不加检查，同类问题还会回来。

### 花费与安全阀

- 每次运行最多花 `llm.max_usd_per_run` 美元（默认 3）。到上限就停，已完成的结果都会保留，再运行一次同样的命令就从断点继续。
- 每次模型调用的结果都缓存在 `work/<项目>/llm/`。重跑不会重复付费；只有改了提示词（版本号变化）的步骤才会重做。
- DeepSeek 在北京时间工作日 09:00–12:00、14:00–18:00 是高峰价，其余时间半价。用量记录在 `work/<项目>/llm/usage.jsonl`。

## 产出

都在 `work/<项目>/` 下：

- `out/<pack_id>.canon.json`：历史包，在 Canon Engine 里导入。
- `out/report.md`：构建报告。内容包括 `canon-lint` 结果、时间线、每个 HARD 事件的不可变要求、没能对应到实体的名字、别名冲突、模型标出的存疑之处。
- `skeleton.md`：不花钱的骨架（章节、关卡、出场人物、文中明示的日期），可以先人工检查。
- `text/`：解析后的可读剧情文本。`summaries/`、`chapters/`、`entities.json` 是各步骤的中间结果。

## 时间是怎么排的

主时钟是故事主线一侧经历的时间，只往前走（FGO 里就是迦勒底的时间）。

1. 章节按剧情顺序排列。
2. 一章从项目文件里的锚点开始；没有锚点，就在上一章结束后隔 `gap_days` 天开始。
3. 章内按摘要给出的时间提示推进：紧接着、当天稍后、第二天、N 天后、早上/晚上、持续多久。
4. 文中明示的日期也是锚点：关卡标题、正文开头的日期标题、片段里写明的日期。时钟只往前走，所以回忆里的旧日期不算；年份离得太远的也不算（比如月面的 3017 年）。只写了钟点的（“现在是 16 时 30 分”），就把那个片段放到这个时刻。
5. 两个锚点之间的章节平分这段时间；排不下时，就把那一段按比例压缩，保证锚点不动。

特异点等章节写成 Canon Engine 1.15 的**时空框架**（`frames`）：数据里有当地年代、且不是主线当下的章节各成一个框架（时钟是“公元1431年，具体日期不明”这样的标签，因为剧本不给逐日的当地日期）。这些章节里不在主线据点（`frames.default`）发生的事件标上 `frame_id`；只在某一个框架里出现的地点也标上，引擎据此知道场景在哪个时空。主线据点的场景仍在主时间线。

除了锚点，具体日期都是推定的，事件里标为 `basis: editorial`。

FGO 各服把"现在"的年份平移过（同一场景：日服 2017 年 = 国服 2018 年 = 美服 2019 年）。项目设了 `year_region: "JP"`：工具逐个脚本对照日服原文，把国服文本里的年份改成日服的年份；对不上时，用全局统计出的换算。

## 项目文件（`projects/*.json`）

- `atlas`：服务器（`region`）、对齐年份用的服务器（`year_region`）、范围（`wars`：`"main"` 或章节编号列表，可写区间 `[100, 108]`）、关卡类型（`quest_types`）、人物合并（`merge_characters`）。
- `protagonist`：原作主人公的名字、性别（脚本里按性别选字）、id、别名、描述。原作主人公在包里是一个普通人物，和其他角色一样；玩家用自己的 Persona 进入这个世界，不扮演主人公。
- `pack`：包的 id、版本、标题、语言、说明。
- `frames.default`：主线据点的名字（FGO 是迦勒底）。
- `timeline`：`origin_date`（第 0 天）、`gap_days`、`gaps`（按章覆盖间隔）、`anchors`（`{"chapter", "start": "YYYY-MM-DD HH:MM", "basis", "note"}`）。
- `classification.max_hard_per_chapter`：每章最多几个 HARD。
- `generic_aliases`：这部作品里不能当别名的通用词（FGO 的职阶名等）。
- `summary.max_chars`：单个关卡超过多少字就分段摘要（默认 16000）。
- `chapter.max_beats`：一章超过多少个片段就分几次编辑（默认 90）。
- `heal_between_chapters`：到了后面的章节仍未结束的伤势按“已恢复（编辑推定）”处理（默认开）。

## 维基篇章（`wiki_arcs`）

魔禁没有可下载的剧本，来源是两部维基：灰机魔禁维基（中文：篇章页、时间线、日期考据）与英文 Toaru Wiki（fandom：篇章页、各人物页的“Chronology”）。项目 `projects/toaru.json` 列出全部篇章（`arcs`：id、标题、起止日期、各来源的页面名）。

- `fetch`：两部维基都拒绝普通 HTTP 客户端，所以用无头浏览器下载（`cpb/tools/wiki_fetch.cjs`，需要 Playwright；项目里 `wiki.fetch` 写下载任务）。页面存在 `work/toaru/raw/`。
- `corpus`：每个篇章一章；中文资料（篇章页、时间线条目、考据段）加英文篇章页。英文篇章页很薄（短于各人物经历合计的 `chronology_when_page_below` 倍）时，加上各人物对这一篇的经历。附上从中文维基信息框得到的“英文→中文”译名对照。超过 `summary.max_chars` 的篇章按英文资料分几部分，每部分都附全篇中文资料。
- `summarize`：一个篇章（或一部分）一次调用，提示词见 `prompts.SUMMARY_WIKI_*`：多份资料讲同一件事要合并；每个片段给出日期（YYYY-MM-DD）和钟点。
- `dedupe`：分部分摘要的篇章、几份经历讲同一件事，都会产生重复片段；模型列出重复组，代码合并（保留最长的经过、全部人物与变化）。时间重叠的篇章两两再查一遍，每一对候选再单独核对一次（并错会丢掉一件事，所以宁缺毋滥）。
- `chapters`、`entities`、`build`：同上。时间：项目的 `arcs` 给每篇的起止日期（来自资料的年表），有日期的片段放在那天那个钟点，中间的按时间提示排开、必要时压缩；同一段时间的几篇（超电磁炮与禁书目录的同一个七月）按时间交错排列，不是一篇接一篇。

## 已知的局限

- 一个从者只有一个实体。在特异点被消灭写成"已消灭"，之后再出现时引擎的检查会提示。这里不区分不同个体（如奥尔良的贞德与迦勒底召唤的贞德）。
- 活动剧情、幕间物语默认不在范围内（`quest_types: ["main"]`）。可以加上 `"event"`、`"friendship"`，但量会大很多。
- 模型偶尔会给出空的 JSON（DeepSeek 的 JSON 模式在长输入、低温度下的毛病）。工具会自动换条件重试，章节步骤直接不用 JSON 模式。

- 事件摘要比手写的包长（平均约 500 字）。在 SillyTavern 里把上下文大小设足：测试环境默认的 8192 tokens 放不下 Canon 的上下文，引擎会报“context capacity”。在本机的测试版 SillyTavern 里，试做包和 1252 个事件的全量（假模型）包都能正常绑定、跑完回合，绑定约 1.4 秒。

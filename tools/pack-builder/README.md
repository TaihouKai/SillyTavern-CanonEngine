# canon-pack-builder（Canon Engine 历史包生成工具）

把一部作品的剧情原文（游戏脚本、维基页面……）做成 Canon Engine 的历史包（`.canon.json`）。

机械的部分全由代码完成：下载、解析、谁在场、日期、时间线、组装、校验。只有"读懂剧情写摘要"这类需要理解的部分才交给便宜的模型（默认 DeepSeek Flash）。

目前有两个来源适配器：**Atlas Academy（FGO 游戏数据，`atlas`）**和**维基篇章（`wiki_arcs`，魔禁用）**。核心流程与具体作品无关，换一部作品只需要换一个适配器。

## 准备

1. 需要 Python 3.10 以上（只用标准库，不用 `pip install`）和 Node（用来运行 Canon Engine 自带的 `canon-lint`）。
2. 把 `config.example.json` 复制为 `config.json`，在 `llm.api_key` 填入你的 DeepSeek API key。也可以不写进文件，改用环境变量 `CPB_API_KEY`。
3. `config.json` 里的 `canon_lint` 指向 Canon Engine 的 `dist/canon-lint.mjs`。工具放在 Canon Engine 仓库的 `tools/pack-builder/` 下，默认路径 `../../dist/canon-lint.mjs` 就是它。
4. 维基来源（`wiki_arcs`）下载时用 Playwright：`npm i playwright && npx playwright install chromium`，或用环境变量 `PLAYWRIGHT_PATH` 指向已装好的 Playwright。

`config.json` 和 `work/` 都不会进 git：前者放着你的 key，后者放着下载的原文和生成的包。

## 用法

在本目录下运行：

```
python -m cpb <命令> -p <项目>
```

`-p` 是 `projects/` 下的项目名，默认 `fgo-cn`。另有 `fgo-cn-sample`（只含冬木和奥尔良两章），适合先试一下效果。

| 命令 | 做什么 | 花钱吗 |
|---|---|---|
| `fetch` | 下载数据和剧情脚本，解析成"语料"，扫描日期，生成骨架报告 | 免费 |
| `estimate` | 估算剩下的模型步骤要花多少钱 | 免费 |
| `summarize` | 模型逐个关卡写结构化摘要（起因/动机/经过/结果……） | 💰 主要花费 |
| `chapters` | 模型逐章判定 HARD/SOFT/FREE、事件关联、伤势何时结束等 | 💰 少量 |
| `entities` | 模型为人物、地点、组织写一句话描述和别名 | 💰 少量 |
| `build` | 代码排时间线、组装包、跑 `canon-lint`、写报告（之前生成过的开局状态、死亡判断、状态判断、常态、思考方式会一并写进去） | 免费 |
| `mind` | 模型为包里有维基页面的人物写「思考方式」：遇事愿意花多少心思想（很少 / 看情况 / 总在想）、想得多好、怎么解决问题；写进包里（`--pack`、`--out` 同上） | 💰 少量 |
| `lasting` | 模型判断组织、地点、物品的每条状态是持续的还是一时的；一时的（停电、正在遭受的袭击、高温）从包的状态里去掉（`--pack`、`--out` 同上） | 💰 极少 |
| `start` | 开局状态：模型按每个组织自己的页面和包里的成员变化，说出它在故事里出场时的成员和首领；然后重新 `build` | 💰 极少 |
| `deaths` | 死后仍在场的人：模型判断是真死（之后是尸体、回忆、幽灵）、复活，还是根本没死；然后重新 `build` | 💰 极少 |
| `nature` | 模型为包里的人物写「常态」：能力、体质或非人之身在日常里的样子，按事件分版本；写进包里（`--pack` 指定别的包，`--out` 另存） | 💰 少量（魔禁 553 人约 $0.25） |
| `run` | 从 `fetch` 到 `build`（进入花钱的步骤前会先问你）；之后依次 `deaths`、`start`、`lasting`、`nature`、`mind`（各自的结果在下次 `build` 时自动套用） | 💰 |
| `status` | 查看每章做到哪一步了 | 免费 |

常用选项：
- `--chapters w100,w101`：只处理这几章。
- `--limit 5`：只摘要 5 个关卡，用来试水。
- `--mock`：用假模型跑通整个流程，不花钱，结果放在单独的文件夹。
- `--yes`：`run` 时不再询问。
- `--offpeak`：只在非高峰时段调用模型，到了高峰就停（已完成的保留，之后再跑同样的命令继续）。

推荐流程：

```
python -m cpb fetch -p fgo-cn-sample       # 先看骨架：work/fgo-cn-sample/skeleton.md
python -m cpb estimate -p fgo-cn-sample
python -m cpb run -p fgo-cn-sample         # 约 $0.2；结果在 work/fgo-cn-sample/out/
```

对试做版满意后，再对 `fgo-cn` 做同样的事。

### 常态（`nature`）

在建好的包上运行（它要用包里的事件）。每个人一次调用，输入是包里的描述、这个人参与的事件（分成开局前的背景和开局后的事件，附包里记录的此人状态变化）和维基上此人的页面。代码再做这些检查：

- 版本 1 是开局（第 0 天）时的样子；之后的版本挂在事件上，要说明持续多久（`for_good` / `until` / `passing`）。临时状态（`passing`，或不到 14 天就结束）丢弃；受伤本身从不算版本，包里本来就记着伤势。
- 后面版本里「新出现的东西」（十字架、电极），开局那一版不能已经提到。
- 版本所在的事件没有记录这个人自己的变化时，要从事件摘要或维基原文引出依据，否则丢弃。
- 不写剧情：和此人同场过的人物，名字不许出现在「平时 / 使用 / 旁人」里（会退回重写）；再由一次检查删掉只发生过一次的事、绰号、传闻、台词。

- 最后一步按版本判断「能力能得知什么」（`perceives`：读心、记忆、情绪、看穿遮挡、定位、识破谎言、读取过去，附条件），Canon 据此决定读心者面前秘密是否开放。只看已写好的常态，一个人一次很短的调用（魔禁 305 人约 $0.015）。

结果在 `work/<项目>/nature/<人物 id>.json`（含丢弃的版本和删掉的句子），可以逐个查看。

### 思考方式（`mind`）

给包里有自己维基页面的人物写（路人、只在剧情里出现过的人没有）。每人一次调用，输入是包里的描述和维基页面。写倾向（`deliberation`）、水平（`sharpness`）和做法等几项，倾向和水平分开：肌肉派可以很敏锐，只是平时不想。和常态一样只写规律、不写剧情：和此人同场过的人物名字不许出现（会退回重写）。资料太少写不出来的回答 `none`。Canon 在游戏里照这个写人，并替「看情况」「总在想」的人做角色盘算。结果在 `work/<项目>/mind/<人物 id>.json`；`build` 时会一并写进包里。

### 开局状态（`start`）

事件只写谁加入、谁离开；一个组织在第一次变化之前有谁，得看它自己的页面。这一步给每个有页面或有成员变化的组织调用一次：输入它的页面、包里它的成员变化（按时间）、它最早的几次出场，以及页面或变化里点过名的人物（只能从这些人里选，代码检查 id）。结果在 `work/<项目>/start/<组织 id>.json`；`build` 时每个起始成员从他自己在故事里出场起才算加入（在那之后第一个和他或这个组织有关的事件上加入；他先被写到离开，就在离开之前），不放在“故事开始时”，否则后来才成立的组织（格雷姆林）在故事开始时就有成员。哪个事件里都没有的人才进初始状态。组织的状态写明瓦解、覆灭、解散时，成员和首领一并清空。

### 死后仍在场（`deaths`）

一个片段写了“死亡”，这个人之后却还在别的片段的在场人物里：可能真死了（之后是尸体、回忆、幽灵、替身），可能复活了，也可能只是被认为死了（落海获救）。这一步把每个这样的人的死亡片段和之后出场的几个片段交给模型判断。复活的在之后第一次出场时活过来，并回到死亡时离开的组织；没死的，死亡改为“下落不明（被认为已死亡）”，到再出场时结束。判断存在 `work/<项目>/deaths.json`，`build` 自动套用。

### 状态是否持续（`lasting`）

事件给组织、地点、物品写的状态，会一直作为现状，直到下一个事件写新的状态，所以一时的情况会挂上几个月（魔禁：学园都市第一晚的「八成区域停电」一直是它的状态）。这一步把这些状态每 40 条一批交给模型，判断是持续的（瓦解、被解体、公开承认魔法存在、结盟）还是一时的；一时的从事件的效果和结果里去掉（事件本身的叙述里还在），HARD 事件绑定的结果不动。判断存在 `work/<项目>/lasting.json`，按实体和状态记，`build` 时自动套用，不再调用模型。人物的状态不在这一步。

### 花费与安全阀

- 每次运行最多花 `llm.max_usd_per_run` 美元（默认 3）。到上限就停，已完成的结果都会保留，再运行一次同样的命令就从断点继续。
- 每次模型调用的结果都缓存在 `work/<项目>/llm/`。重跑不会重复付费；只有改了提示词（版本号变化）的步骤才会重做。
- DeepSeek 在北京时间工作日 09:00–12:00、14:00–18:00 是高峰价，其余时间半价。用量记录在 `work/<项目>/llm/usage.jsonl`。

## 产出

都在 `work/<项目>/` 下：

- `out/<pack_id>.canon.json`：历史包，在 Canon Engine 里导入。
- `out/report.md`：构建报告。内容包括 `canon-lint` 结果、时间线、每个 HARD 事件的不可变要求、没能对应到实体的名字、别名冲突、模型标出的存疑之处。
- `skeleton.md`：不花钱的骨架（章节、关卡、出场人物、文中明示的日期），可以先人工检查。
- `text/`：解析后的可读剧情文本。`summaries/`、`chapters/`、`entities.json` 是各步骤的中间结果。

## 时间是怎么排的

主时钟是故事主线一侧经历的时间，只往前走（FGO 里就是迦勒底的时间）。

1. 章节按剧情顺序排列。
2. 一章从项目文件里的锚点开始；没有锚点，就在上一章结束后隔 `gap_days` 天开始。
3. 章内按摘要给出的时间提示推进：紧接着、当天稍后、第二天、N 天后、早上/晚上、持续多久。
4. 文中明示的日期也是锚点：关卡标题、正文开头的日期标题、片段里写明的日期。时钟只往前走，所以回忆里的旧日期不算；年份离得太远的也不算（比如月面的 3017 年）。只写了钟点的（“现在是 16 时 30 分”），就把那个片段放到这个时刻。
5. 两个锚点之间的章节平分这段时间；排不下时，就把那一段按比例压缩，保证锚点不动。

特异点等章节写成 Canon Engine 1.15 的**时空框架**（`frames`）：数据里有当地年代、且不是主线当下的章节各成一个框架（时钟是“公元1431年，具体日期不明”这样的标签，因为剧本不给逐日的当地日期）。这些章节里不在主线据点（`frames.default`）发生的事件标上 `frame_id`；只在某一个框架里出现的地点也标上，引擎据此知道场景在哪个时空。主线据点的场景仍在主时间线。

除了锚点，具体日期都是推定的，事件里标为 `basis: editorial`。

FGO 各服把"现在"的年份平移过（同一场景：日服 2017 年 = 国服 2018 年 = 美服 2019 年）。项目设了 `year_region: "JP"`：工具逐个脚本对照日服原文，把国服文本里的年份改成日服的年份；对不上时，用全局统计出的换算。

## 项目文件（`projects/*.json`）

- `atlas`：服务器（`region`）、对齐年份用的服务器（`year_region`）、范围（`wars`：`"main"` 或章节编号列表，可写区间 `[100, 108]`）、关卡类型（`quest_types`）、人物合并（`merge_characters`）。
- `protagonist`：原作主人公的名字、性别（脚本里按性别选字）、id、别名、描述。原作主人公在包里是一个普通人物，和其他角色一样；玩家用自己的 Persona 进入这个世界，不扮演主人公。
- `pack`：包的 id、版本、标题、语言、说明。
- `frames.default`：主线据点的名字（FGO 是迦勒底）。
- `timeline`：`origin_date`（第 0 天）、`gap_days`、`gaps`（按章覆盖间隔）、`anchors`（`{"chapter", "start": "YYYY-MM-DD HH:MM", "basis", "note"}`）。
- `classification.max_hard_per_chapter`：每章最多几个 HARD。
- `generic_aliases`：这部作品里不能当别名的通用词（FGO 的职阶名等）。
- `summary.max_chars`：单个关卡超过多少字就分段摘要（默认 16000）。
- `chapter.max_beats`：一章超过多少个片段就分几次编辑（默认 90）。
- `heal_between_chapters`：到了后面的章节仍未结束的伤势按“已恢复（编辑推定）”处理（默认开）。

## 维基篇章（`wiki_arcs`）

魔禁没有可下载的剧本，来源是两部维基：灰机魔禁维基（中文：篇章页、时间线、日期考据）与英文 Toaru Wiki（fandom：篇章页、各人物页的“Chronology”）。项目 `projects/toaru.json` 列出全部篇章（`arcs`：id、标题、起止日期、各来源的页面名）。

- `fetch`：两部维基都拒绝普通 HTTP 客户端，所以用无头浏览器下载（`cpb/tools/wiki_fetch.cjs`，需要 Playwright；项目里 `wiki.fetch` 写下载任务）。页面存在 `work/toaru/raw/`。
- `corpus`：每个篇章一章；中文资料（篇章页、时间线条目、考据段）加英文篇章页。英文篇章页很薄（短于各人物经历合计的 `chronology_when_page_below` 倍）时，加上各人物对这一篇的经历。附上从中文维基信息框得到的“英文→中文”译名对照。超过 `summary.max_chars` 的篇章按英文资料分几部分，每部分都附全篇中文资料。
- `summarize`：一个篇章（或一部分）一次调用，提示词见 `prompts.SUMMARY_WIKI_*`：多份资料讲同一件事要合并；每个片段给出日期（YYYY-MM-DD）和钟点。
- `dedupe`：分部分摘要的篇章、几份经历讲同一件事，都会产生重复片段；模型列出重复组，代码合并（保留最长的经过、全部人物与变化）。时间重叠的篇章两两再查一遍，每一对候选再单独核对一次（并错会丢掉一件事，所以宁缺毋滥）。
- `chapters`、`entities`、`build`：同上。时间：项目的 `arcs` 给每篇的起止日期（来自资料的年表），有日期的片段放在那天那个钟点，中间的按时间提示排开、必要时压缩；同一段时间的几篇（超电磁炮与禁书目录的同一个七月）按时间交错排列，不是一篇接一篇。

## 已知的局限

- 一个从者只有一个实体。在特异点被消灭写成"已消灭"，之后再出现时引擎的检查会提示。这里不区分不同个体（如奥尔良的贞德与迦勒底召唤的贞德）。
- 活动剧情、幕间物语默认不在范围内（`quest_types: ["main"]`）。可以加上 `"event"`、`"friendship"`，但量会大很多。
- 模型偶尔会给出空的 JSON（DeepSeek 的 JSON 模式在长输入、低温度下的毛病）。工具会自动换条件重试，章节步骤直接不用 JSON 模式。

- 事件摘要比手写的包长（平均约 500 字）。在 SillyTavern 里把上下文大小设足：测试环境默认的 8192 tokens 放不下 Canon 的上下文，引擎会报“context capacity”。在本机的测试版 SillyTavern 里，试做包和 1252 个事件的全量（假模型）包都能正常绑定、跑完回合，绑定约 1.4 秒。
